What Is an MCP Server?

An MCP server is a capability provider in the Model Context Protocol that exposes tools, resources, and prompts to connected clients. Servers implement the MCP specification and communicate with clients via JSON-RPC over stdio or Streamable HTTP. When a client sends a tools/list request, the server returns its available capabilities for the LLM to choose from.

An MCP server is the capability provider in the Model Context Protocol. While MCP clients (inside AI applications like Claude Desktop or Cursor) initiate connections, servers respond to those connections by exposing the tools, resources, and prompts available to connected clients.

The MCP specification, introduced by Anthropic in November 2024 and now stewarded by the Linux Foundation, defines how servers communicate with clients. The MCP specification mandates that servers implement four core capabilities:

  • tools/list — returns available tools with name, description, and inputSchema
  • tools/call — executes a named tool with provided arguments
  • resources/list — returns available resources (read-only data)
  • prompts/list — returns available prompt templates

The MCP SDK has recorded 97 million monthly downloads as of early 2026 (Source: Lushbinary MCP ecosystem report, March 2026), reflecting the rapid adoption of MCP servers across the AI developer ecosystem. With 13,000+ MCP servers available on GitHub, servers span every domain from code repositories to design files to database access.

When a client connects to an MCP server, it first sends a tools/list request. The server responds with all available tools — each tool includes a natural language description that the LLM uses to decide when to invoke it. This discovery mechanism is what makes MCP servers interoperable: any client can connect to any server and discover its capabilities without custom integration code.

Production MCP servers differ from development examples in one critical way: security. Toolradar's scan of 2,181 MCP endpoints (April 2026) found that 52% of remote MCP servers become unresponsive within 30 days, and 66% of scanned servers had at least one security vulnerability. Enterprise deployments require monitoring, authentication, and connection health checks that basic server implementations omit.

MCP Server vs MCP Client: The Architecture

The MCP architecture separates concerns clearly: servers provide capabilities, clients consume them, and hosts run one or more clients. Understanding this separation helps you design better AI systems and debug connection issues.

Key distinction from the client perspective: clients don't know which other clients are connected to the same server, and servers don't track which clients are using them. A client sends a tools/list request and receives a list of available tools. The server simply responds to requests — it doesn't track state about which client made which request.

This stateless design is intentional. MCP servers are designed to be lightweight and composable — you can connect multiple clients to the same server, or a single client to multiple servers, without modifying the server's implementation. The MCP specification handles the protocol negotiation, so servers remain simple capability providers regardless of how many clients connect.

For developers building AI systems, this means: your choice of MCP server is independent of your choice of MCP client. Claude Desktop, Cursor, Cline, and any other MCP-compatible application can all connect to the same servers. The MCP protocol enables this interoperability by standardizing the communication interface.

1. GitHub MCP

Domain: Code Repository Most Popular Interface: stdio / HTTP

GitHub MCP exposes tools for interacting with GitHub repositories — creating and managing issues, pull requests, code search, and file operations. Built by GitHub's official team at github.com/github/github-mcp-server, it's the standard for AI-powered developer workflow automation. The server integrates with GitHub's API to provide natural language interfaces for repository management. MCP servers expose tool calling interfaces that any MCP-compatible client can invoke through standardized JSON-RPC requests.

Best for: teams building AI coding assistants that need to interact with code repositories, automate issue triage, or generate PR descriptions. The GitHub MCP reduces the friction between AI reasoning and repository operations.

2. Figma MCP

Domain: Design Interface: Plugin-based

Figma MCP exposes tools for interacting with Figma design files — retrieving components, accessing design tokens, reading comments, and navigating file structures. This enables AI assistants to understand design context and generate code that matches design specifications.

Best for: design-to-code pipelines where AI needs to understand visual designs and convert them into implementation. Also useful for accessibility audits — AI can read design files and flag accessibility issues.

3. Linear MCP

Domain: Project Management Interface: stdio / HTTP

Linear MCP exposes tools for managing Linear workspaces — creating and updating issues, managing projects and cycles, and interacting with comments. Linear's API-first approach makes it a natural fit for AI workflow automation.

Best for: engineering teams building AI assistants that handle sprint planning, issue triage, or status updates. The Linear MCP connects AI reasoning to operational project management.

4. Sentry MCP

Domain: Error Monitoring Interface: stdio

Sentry MCP exposes tools for interacting with Sentry's error tracking — looking up errors by fingerprint, creating issues, and retrieving stack traces. This is particularly valuable for AI coding assistants that generate code and need to debug their own output.

Best for: AI systems that write code and need to self-correct based on runtime errors. When an AI generates code that triggers a Sentry error, it can look up the details, understand the stack trace, and fix the issue without human intervention.

5. Context7

Domain: Documentation Developer Favorite Interface: stdio

Context7 MCP exposes tools for retrieving contextual documentation from project repositories. It indexes code, README files, and API documentation, then provides tools for semantic search and context retrieval. This is the foundation for AI code assistants that need accurate project-specific context.

Best for: AI coding assistants that need to understand a codebase before generating suggestions. Context7 provides the "knowledge" layer that makes AI code generation project-aware rather than generic.

6. Brave Search MCP

Domain: Web Search Interface: stdio

Brave Search MCP exposes tools for web and local search — retrieving current information from the web, searching for images, and running local Brave Search queries. Unlike API-based search that requires paid subscriptions, Brave Search provides a privacy-respecting alternative with generous free tiers.

Best for: AI systems that need real-time information but want to avoid the cost and privacy implications of Google or Bing APIs. Brave Search MCP is popular for AI research assistants and fact-checking workflows.

7. Supabase MCP

Domain: Database Interface: stdio

Supabase MCP exposes tools for interacting with Supabase projects — running SQL queries, inspecting schemas, and managing auth. This enables AI assistants to query databases directly, generate SQL from natural language, and build data-driven applications.

Best for: AI systems that need to interact with data — generating reports from database queries, building dashboards, or automating data workflows. The Supabase MCP bridges AI reasoning and relational data.

8. Notion MCP

Domain: Knowledge Base Interface: API-based

Notion MCP exposes tools for interacting with Notion workspaces — reading and writing pages, searching content, and managing comments. This enables AI assistants to access internal knowledge bases and keep documentation updated based on AI-generated insights.

Best for: teams that use Notion as their primary knowledge management system. AI can read existing documentation, update pages based on new findings, and surface relevant knowledge in response to queries.

MCP Server Examples: How They Work in Practice

Understanding how an MCP server works under the hood helps you evaluate servers, debug connection issues, and build custom servers when needed. Here's a minimal FastMCP server implementation and the JSON-RPC flow that powers tool discovery.

Building a Minimal MCP Server with FastMCP

# Minimal MCP server with FastMCP
# Source: MCP SDK documentation, modelcontextprotocol.io

from fastmcp import FastMCP

mcp = FastMCP("my-server")

@mcp.tool()
def search_docs(query: str) -> str:
    """Search documentation for a query string."""
    return f"Results for: {query}"

@mcp.tool()
def get_doc_content(doc_id: str) -> str:
    """Retrieve the full content of a document by ID."""
    # Implementation would fetch from your doc store
    return f"Content of {doc_id}"

# Run with: fastmcp run my_server.py
# Or connect via: fastmcp dev my_server.py (for development)

The FastMCP decorator-based approach keeps server code minimal. Each decorated function automatically becomes a tool with its name derived from the function name, its description from the docstring, and its input schema from type annotations. The MCP SDK handles the protocol layer — you focus on the business logic.

JSON-RPC Request/Response Flow

When a client connects to a server, the discovery and invocation flow uses JSON-RPC over stdio or Streamable HTTP. Here's what that looks like:

// Client sends tools/list request (client → server via stdio/HTTP)
{"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}}

// Server responds with available tools (server → client)
{"jsonrpc": "2.0", "id": 1, "result": {
  "tools": [
    {"name": "search_docs", "description": "Search documentation for a query string.", "inputSchema": {"type": "object", "properties": {"query": {"type": "string"}}}},
    {"name": "get_doc_content", "description": "Retrieve the full content of a document by ID.", "inputSchema": {"type": "object", "properties": {"doc_id": {"type": "string"}}}}
  ]
}}

// Client invokes a tool (client → server)
{"jsonrpc": "2.0", "id": 2, "method": "tools/call", "params": {
  "name": "search_docs", "arguments": {"query": "authentication best practices"}
}}

// Server returns tool result (server → client)
{"jsonrpc": "2.0", "id": 2, "result": {
  "content": [{"type": "text", "text": "Results for: authentication best practices"}]
}}

The JSON-RPC format is simple by design. Every request includes a jsonrpc version, an id for correlation, a method name, and params. Responses include the same id and a result or error. This simplicity is what makes MCP servers easy to implement and debug. MCP servers expose tool calling interfaces that any MCP-compatible client can invoke through standardized JSON-RPC requests, enabling seamless interoperability across different AI applications and tools.

Single-Purpose vs Meta-Server: A Different Category

Important distinction: This page covers single-purpose MCP servers — tools focused on one domain like GitHub, Figma, or Linear. Qveris operates as a meta-server, which is a different category entirely. This isn't a comparison; it's two distinct architectural approaches for different use cases.

The eight servers above are single-purpose MCP servers — each focuses on one domain and exposes tools specific to that domain. GitHub MCP knows about repositories and pull requests; Figma MCP knows about designs and components. They excel at their domain but require separate connections for each domain you want to access.

A meta-server takes a different architectural approach: instead of focusing on one domain, it aggregates capabilities from multiple providers into a single connection. Qveris operates as a meta-server — one connection gives your AI assistant access to tools across search, maps, weather, documents, financial data, blockchain, healthcare, and more. This capability routing architecture handles the complexity of routing each tool call to the correct provider, so your AI application doesn't need to manage multiple server connections or authentication flows.

The practical difference: if you want to connect to 10 different single-purpose servers, your AI application needs to manage 10 connections, handle 10 authentication flows, and maintain 10 separate server configurations. With a meta-server, one connection covers all domains.

Neither approach is universally better. Single-purpose servers are ideal when you need deep, domain-specific integrations with fine-grained control. Meta-servers are ideal when you want broad capability access with minimal connection management overhead. The meta-server approach excels at capability routing — intelligently directing tool calls to the appropriate underlying provider based on the user's request. Instead of your AI application needing to know which of 10 different servers handles search versus maps versus finance, the meta-server handles that routing internally. This unified capability routing reduces integration complexity while maintaining access to thousands of distinct capabilities.

Deployment Options for MCP Servers

MCP servers can be deployed in several ways depending on your requirements for security, scalability, and operational overhead. The three main patterns are local process, remote service, and managed platform.

Local Process (stdio)

The simplest deployment: run the MCP server as a local process and connect via stdio. This works well for development, CLI tools, and single-user workflows. Claude Code and other CLI-based clients typically use stdio transport.

Configuration is minimal — you point your MCP client at the process and it handles the connection. The downside: the server is tied to the local machine, which limits team sharing and remote access.

Remote Service (Streamable HTTP)

For production deployments where multiple clients need to connect, deploy the MCP server as a remote service with Streamable HTTP transport. This requires implementing authentication (API keys, OAuth, or mTLS) and connection health monitoring.

According to Toolradar's endpoint scan, 52% of remote MCP servers become unresponsive within 30 days — often due to missing health checks and auto-restart configuration. Production deployments need monitoring for connection health and automatic recovery on failure.

Managed Platform

Managed MCP platforms like Apigene, Prefect, and AWS Bedrock handle the operational complexity — authentication, monitoring, scaling, and security — so you focus on the server logic. What is the difference between an MCP server and an MCP client?
An MCP server is the capability provider — the service that exposes tools and data. An MCP client is the component inside the AI application (the host) that connects to servers and manages communication. Clients like Claude Desktop or Cursor expose one or more MCP clients, each connecting to one or more servers. The server doesn't know which client is using it — it simply responds to requests.
